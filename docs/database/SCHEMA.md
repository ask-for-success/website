# Implemented Database Schema

Django models and migrations are the source of truth. [AFS_Database.dbml](./AFS_Database.dbml) represents only the implemented schema; planned models must not be added early.

## `users` table

| Column | Purpose |
|---|---|
| `id` | Immutable UUID primary key. |
| `email` | Required case-insensitive unique login identifier. |
| `first_name` | Required first name. |
| `last_name` | Required last name. |
| `phone_number` | Required unique contact number. |
| `password` | Password hash generated by Django. |
| `is_active` | Allows or blocks authentication. |
| `is_staff` | Controls Django administration access. |
| `is_superuser` | Django superuser flag. |
| `created_at` | Account creation timestamp. |
| `updated_at` | Last update timestamp. |

Future domains reference `users.id` instead of duplicating account data.

## Technical token tables

SimpleJWT creates outstanding and revoked refresh-token tables through its own migrations. These are technical authentication tables, not business models.

## Access-control tables

Global roles and capability assignments use Django's built-in group and permission tables. The approved matrix is documented in the [authorization guide](../api/AUTHORIZATION.md); DBeaver may be used to inspect these tables, but assignments should go through the API or Django administration.

## User-model boundary

Membership, applications, business roles, and the national ID number do not belong to `users`. Their behavior is defined in the [functional scope](../business/BACKEND_SCOPE_V1.md) and will be modeled only when each domain is implemented.
